# identity-server — ИЗОЛИРОВАННЫЙ сервер: телефоны, пароли, ничего больше

**Автор: R_stepanov**

Это третий, отдельный сервис в проекте (не путать с `messenger-server`).
Его единственная задача — хранить самые чувствительные данные:
**номера телефонов** (зашифрованы) и **пароли хранилища "Данные"**
(хешированы). Больше здесь ничего нет — ни сообщений, ни истории чатов.

## Почему отдельно

Если когда-нибудь взломают основной сервер чатов (`messenger-server`) —
злоумышленник получит переписки, но **не получит номера телефонов и
пароли** — они физически лежат в другой базе данных, на другом сервере,
и достучаться до identity-server напрямую из интернета невозможно даже
зная его адрес: каждый запрос обязан нести секретный `x-internal-key`,
который знают только сами сервера, не браузер пользователя.

```
Браузер → messenger-server (открыт всем) → identity-server (только
                                             по внутреннему ключу,
                                             messenger-server↔identity)
```

## Куда заливать

Отдельный **Render Web Service** + отдельный **Render PostgreSQL** — не
тот же, что у messenger-server. Итого на Render у тебя будет: 2 базы
данных + 2 web-сервиса + фронтенд на Netlify = 3 отдельных деплоя. Да,
это больше шагов, чем один сервер — это и есть цена настоящей изоляции.

## Настройка

```bash
npm install
cp .env.example .env
```

Впиши:
- `DATABASE_URL` — адрес НОВОЙ, отдельной базы Postgres
- `JWT_SECRET` — **точно такой же**, как в `.env` у `messenger-server`
  (иначе токены входа не совпадут)
- `PHONE_ENCRYPTION_KEY`, `PHONE_HASH_KEY` — свои случайные строки
- `INTERNAL_API_KEY` — длинная случайная строка; без неё сервер вообще
  откажется стартовать (специально, чтобы не забыл поставить защиту)

Эту же строку `INTERNAL_API_KEY` пропиши в `.env` у `messenger-server`
как `IDENTITY_INTERNAL_KEY` — это общий "пароль" между двумя серверами.

```bash
npm start
```

## Что здесь физически хранится

| Поле | Как хранится |
|---|---|
| Номер телефона | зашифрован AES-256-GCM (`phone_enc`) + отдельный HMAC-отпечаток для поиска (`phone_hash`, сам номер по нему не восстановить) |
| Пароль хранилища "Данные" | bcrypt-хеш, необратимо |
| Записи в хранилище (пароли/заметки пользователя) | AES-256-GCM, ключ выводится из пароля пользователя на лету и хранится только в оперативной памяти 5 минут |
| Юзернейм | в открытом виде (не секрет — виден собеседникам в чате) |

Даже с полным дампом базы данных этого сервера — без `PHONE_ENCRYPTION_KEY`
номера не восстановить, а пароли хранилища необратимо хешированы.

## Эндпоинты (все под `/internal/*`, требуют заголовок `x-internal-key`)

- `POST /internal/auth/request-code`, `POST /internal/auth/verify-code`
- `GET /internal/users/:id`, `GET /internal/users/search`,
  `PATCH /internal/users/:id/username`, `GET /internal/users/:id/phone`
  (только свой номер, с проверкой токена)
- `GET/POST /internal/admin/*` (список/бан — решение "кто админ"
  принимает messenger-server, этот сервис просто исполняет)
- `GET/POST /internal/vault/*` — хранилище "Данные" целиком здесь
